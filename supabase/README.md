# FieldCentral Supabase foundation

The baseline migration in `migrations/202608050001_initial_fieldcentral_schema.sql`
creates the core production persistence model. The follow-up migration
`migrations/202608050002_business_bootstrap_and_client_rpcs.sql` completes the
first live application slice.

Apply migrations in filename order.

## Tenant and role model

- Every auth user has at most one row in `profiles`, so a user belongs to one
  business in this release.
- Creating a `businesses` row with `owner_user_id = auth.uid()` provisions the
  owner profile, Australian defaults, quote/job/invoice number sequences, and
  default quote and invoice templates in the same transaction.
- `owner` and `co_owner` are management roles. `technician` is an operational
  role with no configuration, lead-management, quote, invoice, or payment
  mutation access.

| Area | Owner / co-owner | Technician |
| --- | --- | --- |
| Business, templates, questionnaires | Read/write | Business basics read-only |
| Clients and service addresses | Read/write | Read-only |
| Job requests, quotes, invoices, payments | Read/write | No direct access |
| Jobs and assignments | Read/write | Read all; update assigned execution state only |
| Assigned-job notes and attachments | Read/write | Create and manage own records |
| Audit events | Read | No direct access |

RLS is enabled on every API-facing table. Security-definer helpers have explicit
`search_path` values and are revoked from API roles unless they are intentional
RPC endpoints.

## First-owner bootstrap

`bootstrap_current_user_business` serialises provisioning per auth user. It
returns an existing active membership or creates exactly one owner business,
owner profile, Australian defaults, document sequences, and default templates.
It derives identity from `auth.uid()` and is executable by `authenticated` only.

## Client persistence

The second migration adds explicit client lifecycle and preferred-contact
columns, service cadence, address active state, and recoverable client archive.

- `save_client_with_details` validates a bounded JSON payload and atomically
  saves the client, its primary contact, and its active service-property set.
- Existing address ids are updated in place. Removed service addresses are
  marked inactive so historical operational records keep their foreign keys.
- `archive_client` removes the client from active work without deleting its
  job, quote, invoice, or audit history.
- Direct authenticated hard deletion from `clients` is revoked.
- Both client detail tables now emit append-only audit events.

All client RPCs derive the current business and management role in PostgreSQL;
the browser never supplies a trusted tenant id or role.

## Questionnaire share links

Generate at least 32 characters of cryptographically random data in the server
runtime. Pass the raw token once to `create_questionnaire_invitation`; only its
SHA-256 digest is stored. Email or copy the raw token in the public URL. The
public page should call `get_public_questionnaire`, then submit through
`submit_questionnaire_response`. Invitations are single-use and expire.

Never log the raw bearer token or put it in analytics payloads.

## Documents and money

- Quote, job, and invoice numbers are allocated atomically per business.
- Line subtotal, tax, and total values are generated by PostgreSQL; parent
  totals are refreshed by triggers.
- Invoice `document_status` is independent from `payment_status`.
- Payments represent manual/external records only; no card processor or secret
  credential is assumed by this schema.
- Money is stored as fixed-scale numeric values. Application code should still
  format amounts with the business currency and locale.

## Local apply and validation

With the Supabase CLI installed and a local project initialised:

```bash
supabase start
supabase db reset
supabase db lint --level warning
supabase gen types typescript --local > src/types/database.ts
npm run check:migrations
```

The migration targets Supabase Postgres 15 or newer. It uses PostgreSQL's
column-list form of `ON DELETE SET NULL` so tenant keys remain non-null when an
optional related record is removed.

The generated TypeScript file should be refreshed after every schema migration;
it is intentionally not hand-maintained here.

The repository currently uses explicit runtime DTO validation until generated
local types can be produced from a running Supabase stack.

## Development data

Keep development fixtures in `supabase/seed.sql` only after the product fixture
set is agreed. Use fictional Australian contacts and addresses, create auth
users through supported Supabase tooling, and never commit API keys, service-role
tokens, raw questionnaire tokens, or copied customer data.

Before production launch, add storage bucket policies for job attachments and
document PDFs. Use paths beginning with the authenticated member's business id,
for example `{business_id}/{job_id}/{object_id}`, and validate both the path and
the related database row in the policy.
